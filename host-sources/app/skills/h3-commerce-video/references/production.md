# 正式H3包与工作流执行

## 输入检查

读取 [固定输入与素材规则](assets.md)，实际查看用户图片。默认四图：开场场景、商品主图、同款补充证据、关键细节或操作。按已选画面形式核对图1的人物场景或商品场景；纯商品旁白不需要模特素材。槽位数量和编号固定，每槽内容由品类规则确定。输出原文件名→角色→槽位的对应表，检查同一SKU、颜色、结构及展示范围。图片错位或冲突时列具体重传项；四图缺项先做受限方案，使用两图版须由用户选择。

商品资料卡提供品类、名称/款式、目标使用场景、已有卖点和必要使用条件。按实际资料选择最相关的一两条理由，已有资料直接归入这些字段，不要求用户重复填写。图片约束人物和SKU外观，商品资料支持功效、口味、规格与使用信息，二者分别核对。不同品类沿用生成与拼接参数，重新选择展示动作与购买理由。

中文、9:16、轻快自然带货、两段。`presentation_mode`记录`presenter`（人物讲解，默认）或`product_voiceover`（纯商品旁白）；同一口播取舍规则用于两种形式。已有足够素材与事实时直接产出，不重复询问默认项。化妆品、食品等缺少核心用途、口味或功效资料时，列最少补充项并交付可支持的部分；不把长篇包装外观介绍冒充完整销售方案。

价格、材质、容量、功效、认证及促销条件只能来自用户提供的事实。图片区分“能看到的外观”与“不能从图片证明的性能或体感”。单只/成对、左右脚、件数与部件数量也须按实图核对。搭配建议用建议口吻；亲身试用经历、舒适度、承重、味道等需要用户资料，不能由模特动作代替证据。不得把生成的多角度图当作真实商品结构证据。

## 编排

先完成[文案指南](selling-copy.md)的取舍表和逐句审稿，按实际内容判断完整方案、短稿或事实待补。通过的正文才分配动作、镜头和两段时长。短稿保留短稿状态，正式30秒双段包待补。

先锁定产品SKU与颜色结构、场景、光线、声音身份和口吻；人物形式另锁定人物与服装。生成一个 `immutable_identity_block`，原样复制到两段 subject_definitions；B 仅在其后追加真实接入的音频参考定义。读取 [提示词规则](prompts.md) 和 [配套工作流契约](workflow-contract.md)，确认版本、图片槽位、音频连接和验收状态。

第一段让观众理解商品与自己有什么关系，并讲清核心理由；第二段承接实际结束状态，推进另一条选购依据或解决实际顾虑，再自然收尾。需要专门讲解的用法按购买问题选入，其余简单动作写在分镜中。每段2–3个镜头，口播跨镜头延续。

每条主打理由同时注明来源、必要购买条件及镜头位置。可见结构用对应特写；有资料支持的功效、口味与使用理由用本模式的讲解声音及相关使用/内容物画面承载，画面不作为性能或体验证据。逐镜头记录开始/结束状态和衔接方式，按[边界规则](prompts.md#边界)区分连续动作与剪切省略；没有依据的操作改成有依据的稳定状态。两种形式都检查商品分镜、比例和动作关系，人物形式另检查本人开口。虚构测试使用明确提供的模拟商品设定，并标为测试资料。

人物形式采用“对镜口播＋商品分镜”，露脸镜头本人开口，商品切镜保持同一人的声音。纯商品形式让所有镜头展示商品、内容物、细节或有依据的使用状态，由独立旁白贯穿两段；逐镜`mouth_visible=false`。两种形式都按台词的具体内容分配画面：讲领口展示领口，讲背面结构展示背面。输出与检查细则见[提示词规则](prompts.md)。

工作流提供的前置帧属于第二段时间预算的一部分；第二段提示词要为这段承接留时间，后续口播只覆盖新增画面。前置帧来自第一段实际输出，用户无需另传。引用视频作为风格参考与真实前置帧引导不是同一接口，不能混称。

## 输出

1. 固定输入验收：资料卡、已支持事实、未确认信息、上传槽位表与具体补充项。
2. 购买方向：目标观众/场景、要回答的选购问题、核心理由及来源、所选开场和收尾方式。
3. 分镜表：逐镜头列出所属段、局部时间、台词、景别与画面职责、对应素材/图片编号、嘴部是否可见及声音来源、开始/结束状态和进入方式；列出镜头图准备方式和缺失素材。两段口播附逐段字数与目标时长。
4. 通过输入与方案验收后交付两段完整六字段提示词，分别放在独立代码块或UTF-8文本文件，能够直接粘贴。输出文件时保存 `prompt-a.txt`、`prompt-b.txt`、`package.md` 和 `result.json`；正式JSON的最低合同见[提示词规则](prompts.md#文件交付与检查)。受限或冲突状态只交付对应的可支持部分与补充说明，不虚构完整可运行包。
5. 工作流使用步骤、固定参数、前置重叠与裁切说明；必须与所用版本的真实节点一致。配套JSON放在本Skill的`assets/workflows/`，交付时复制对应版本到用户输出目录。没有验证过的工作流明确标为待验证。

提示词正文用肯定、可观察的状态描述。禁止事项放在交付包的检查表；不要堆砌进正向提示词。没有用户要求时，不自动上传、生成或剪辑。

## 验收

先检查台词有没有回答本品的购买问题、有没有依靠包装色彩与通用话术填满时长，逐条核对主张来源。再检查图片角色、编号、实际字数、第二段承接和前置帧约定；按分镜表检查具体部位、用途和使用动作是否有对应画面。有 Python 时运行 `scripts/validate_package.py` 检查格式、共享定义、连接引用和字数；脚本不评价销售理由是否成立。执行生成时检查实际帧数、音频时长、接缝画面、可见口型和台词对应画面的出现时间，涉及成妆/使用后外观时执行[参考对照验收](prompts.md#外观参照与呈现强度)，记录失败与重试。静态检查、ASR或抽帧只能证明对应检查项，不能冒充完整听看验收。已生成口播、已写分镜、已生成并验收分镜视频是不同状态。
