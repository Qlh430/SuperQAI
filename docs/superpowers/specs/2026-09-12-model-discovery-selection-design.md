# 模型发现选择与操作按钮优化设计

## 背景

模型服务设置页的“拉取模型”会把上游返回的模型展示在发现区。当前发现区默认勾选全部模型，用户容易在不知情的情况下把整份目录加入当前提供商；底部操作按钮也没有充分区分主次操作。

## 目标

- 拉取结果中，当前提供商已经保存的模型默认勾选。
- 拉取结果中的新模型默认不勾选，由用户明确选择后再加入。
- 保留发现区实时选中数量与现有搜索、分类筛选行为。
- 让“加入所选模型”成为清晰的蓝色主操作，让“取消”成为低强调的次操作，并提供一致的 hover、focus-visible、disabled 状态。

## 方案

沿用现有发现区和草稿状态，不引入新弹窗或额外快捷选择器。

1. `syncModels()` 保留当前表单中的模型配置，用其 ID 集合作为已保存模型集合；`state.modelDiscovery.models` 使用完整的推断结果，而非过滤掉已存在模型。
2. `modelDiscoveryMarkup()` 根据模型 ID 是否位于已保存集合生成 `checked` 属性。已有模型显示选中态，新模型显示未选中态；已保存模型在协议标签旁显示“已保存”状态标识，帮助用户理解默认选择。
3. `addDiscoveredModels()` 继续以 ID 去重，只追加用户选中的、当前不存在的模型，因此已保存模型即使保持勾选也不会重复添加。
4. 发现区 footer 的两个按钮添加语义化 class：主按钮复用设置页蓝色主按钮体系，取消按钮复用次按钮体系；在 `system-settings.css` 中补充 hover、active、focus-visible 与 disabled 样式，并保持移动端布局。

## 数据流与边界

- 拉取失败时维持现有错误提示，不修改发现区状态。
- 上游没有返回已保存模型时，已保存模型仍由 `state.draftProvider` 保留；发现区只展示本次返回的目录。
- 选中数量为 0 时，“加入所选模型”禁用，避免产生无效提交；取消始终可用并清除发现状态。
- 既有搜索、分类筛选只控制可见性，不改变复选框选择状态。

## 验证

- 增加 UI 静态检查，覆盖：发现区包含已保存与新模型、`checked` 由已保存 ID 决定、追加逻辑仍去重、按钮使用主次语义 class。
- 运行 `node --check system-settings-ui.js`。
- 运行 `node tools/check-system-settings-ui.js`，并在可用的浏览器烟测中确认默认勾选、手动选择、取消与按钮状态。
