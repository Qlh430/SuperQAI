# Agent 覆盖率模型角色修正设计

> 状态：已实施并通过 Provider、HTTP、设置页浏览器与真实协议注册表回归。此修正延续现有“站点 Agent 覆盖率”功能，不发起付费模型请求。

## 问题

当前覆盖率把站点内所有模型都按“Agent 主对话模型”检查。因此图片模型会显示“不适用”，而从 `/models` 只拿到名称的 LLM 会默认只有 `llm.chat`，即使所选模型协议支持工具调用，也会显示“缺少工具能力”。这既混淆了模型角色，也把“目录未提供能力元数据”误写成“模型不具备能力”。

## 方案比较

1. **按模型角色与协议契约判断（采用）**：LLM 进入 Agent 主模型覆盖率；图片、视频和音频模型作为 Agent 媒体工具单列。新发现的 LLM 能力从所选模型协议支持的能力中推断，显式保存的能力仍优先。
2. **按模型名称硬编码**：把 GPT、Claude、Gemini 等名称直接列为工具模型。实现快，但遇到代理重命名、新版本或同名兼容服务会持续误判，因此不采用。
3. **覆盖检查时真实调用工具**：结论最强，但每次检查会消耗额度，并可能被余额、限流和临时网络影响。真实可用性继续交给已有“模型测试”和“Agent 验证”，不在这个无费用检查中重复执行。

## 判定与界面

- 具备 `llm.chat` 且模型协议提供 `llm.tools` 的模型，作为 Agent 主模型；同时具备视觉能力时显示可识图。
- 显式配置仅勾选对话、但协议能够提供工具调用时，显示“可启用 Agent”，不再声称模型本身缺少能力。
- 图片、视频、音频模型显示为“Agent 图片工具”“Agent 视频工具”或“Agent 音频工具”，不进入主模型覆盖率分母。
- 协议本身没有工具调用的对话模型才显示“仅支持对话”。协议不可执行的主模型显示“暂不可用”。
- 汇总使用“可完整执行的 Agent 主模型 / Agent 主模型总数”，并附带媒体工具数量；文案明确这是协议与配置检查，不是付费实测。

## 数据流

模型目录对象必须完整传入能力推断，不能只保留 ID。新发现、未显式声明能力的 LLM 先获得通用对话、视觉和工具候选能力，再由协议注册表过滤为协议真正支持的能力。用户显式保存的能力数组不被自动覆盖。

## 验证

- 单元测试覆盖 Agent 主模型、可启用模型、真正的仅对话协议、媒体工具和不可执行协议。
- 协议配置测试覆盖 OpenAI 兼容 LLM、Gemini 原生 LLM以及显式能力不被改写。
- HTTP 测试覆盖目录对象元数据保留、实时覆盖汇总和不泄露密钥。
- 浏览器测试检查主模型分母、媒体工具标签和说明文案。
