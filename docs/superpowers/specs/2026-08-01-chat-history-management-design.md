# GPT 对话历史菜单与批量删除设计

## 背景与根因

GPT 对话历史的三点菜单向下覆盖相邻记录。浏览器复现显示：第一条菜单与下一条记录重叠约 31px；菜单自身为 `z-index: 8`，但每个 `.history-chat-row` 都被最终暗色主题设置为 `isolation: isolate`，形成彼此独立且 `z-index: auto` 的堆叠上下文。后出现的记录因此绘制在前一条菜单上方。历史滚动容器同时使用 `overflow-y: auto`，最后一条记录向下展开时还可能被容器底部裁切。

当前“清空全部”通过 `clearServerHistory(CHAT_HISTORY_API_URL)` 直接删除所有对话，仅有浏览器确认框。用户要求改为与在线生图一致的“管理 → 多选 → 删除所选 → 二次确认”。现有 `/api/history/chat?id=...` 已支持按 id 删除，不需要修改服务端协议。

## 方案选择

菜单修复考虑三种方案：

1. 打开菜单时提高整条记录的堆叠层级，并让最后一条记录向上展开。改动最小，保留现有 DOM、滚动和键盘行为，采用此方案。
2. 将菜单挂到 `body` 并使用 fixed 坐标。能完全脱离裁切，但需要处理滚动、缩放、关闭和焦点返回，复杂度不必要。
3. 把删除按钮作为行内区域展开。不会叠层，但会推动列表并改变用户熟悉的三点菜单交互，不采用。

批量删除直接复用在线生图已验证的管理模式，不引入第三套交互。

## 交互设计

正常模式：

- 历史标题右侧显示“管理”，不再显示“清空全部”。
- 点击对话卡片仍加载对应对话。
- 三点按钮仍打开“删除对话”，用于快速删除单条记录。
- 打开菜单的记录提升到其他记录上方；最后一条记录的菜单向上展开，避免底部裁切。

管理模式：

- 点击“管理”后按钮改为“取消”。
- 三点按钮和单条菜单隐藏，整张对话卡片成为选择热区。
- 顶部显示“已选 N 条”和“全选 / 取消全选”。
- 每条记录显示圆形勾选标记；选中状态使用信号黄边框、背景和勾选图标共同表达。
- 底部显示“删除所选（N）”，没有选择时禁用。
- 第一次点击删除只展开原地确认条：“确定删除 N 条？”、“取消”、“确认删除”。
- 只有确认后才按记录 id 串行删除；选择发生变化时自动退出待确认状态。
- 删除包含当前对话时，删除后新建空白会话并清空消息区。
- 删除成功后退出管理模式并刷新历史；部分失败时刷新列表、移除已经删除的选择，并显示失败状态。

## 状态与无障碍

- 使用 `Set<string>` 保存选中的对话 id；进入或退出管理时清空选择和确认状态。
- 管理按钮使用 `aria-pressed`，对话按钮在管理模式使用 `aria-pressed` 暴露选择状态。
- 选择计数使用 `aria-live="polite"`。
- 所有新增按钮提供 hover、disabled 与 `:focus-visible` 状态。
- 缺少 id 的旧记录仍可正常打开，但在管理模式不可选择。
- 正常模式单条删除、当前会话重置、历史加载和消息保存行为保持不变。

## 技术边界

- 修改集中在 `index.html`、`script.js` 与 `styles.css`。
- 新增源码回归检查 `tools/check-chat-history-management.js`，并加入现有 `precheck`。
- 不修改服务端、历史数据格式、存储路径、聊天消息协议或其他工具页。
- 不引入依赖、外部图标或新的弹窗组件。

## 验证与验收

- 回归检查先因“管理”控件和状态函数缺失而失败，再在实现后转绿。
- `node --check script.js`、新增检查、`npm run check` 与 `git diff --check` 全部通过。
- Playwright 使用隔离的假对话历史，不触碰真实数据，验证：
  - 三点菜单重叠区域的 `elementFromPoint` 命中菜单而不是下一条记录；
  - 最后一条菜单向上展开且位于滚动容器内；
  - 管理模式整卡选择、全选、取消和二次确认状态正确；
  - 第一次点击删除产生 0 个 DELETE；
  - 确认后仅对选中 id 串行发出 DELETE，最大并发为 1；
  - 管理模式退出后卡片恢复加载对话，三点按钮恢复可用；
  - 控制台无新增错误。

验收结果应为：菜单内容完整可点，不被相邻记录或滚动边界遮挡；“清空全部”入口消失；用户只能通过明确选择和二次确认批量删除对话。
