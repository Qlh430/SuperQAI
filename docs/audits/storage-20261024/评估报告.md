## 占用原因及计量

项目原检查逻辑大小 151,422,824,114 字节（141.02 GiB），文件分配空间 151,934,062,184 字节；项目外 Staging 逻辑大小 2,928,876,520 字节（2.73 GiB），分配空间 2,935,063,328 字节。新增审计元数据未全部包含在这个扫描起点的数值里。

主要占用为 `.planning` 82.24 GiB、实际 Portable 下 `.ai-runtime/versions` 40.01 GiB（44 个目录）、`.publish` 11.88 GiB，以及 Golden 2.42 GiB、`.design` 2.33 GiB。它们不是同一层级中可任意重复相加的目录；清单只列互不包含的实际目标。

扫描没有读取凭据内容。Windows DirEntry.stat 的链接计数返回 0，不能用于认定无硬链接；最终改用文件句柄的 FileStandardInfo.NumberOfLinks 重新完整扫描，发现 **24,181 个硬链接文件名，11,454 个文件身份组**（链接数为 2 或 3），所有链接名都在本次扫描范围内。目录累加的分配值因此重复约 **9.31 GiB**。复查时项目与外部 Staging 合计物理文件分配约 **134.99 GiB**，其中包含本次新增审计资料；141.02 GiB 是项目原始逻辑目录累计值，不能全部视为独占物理空间。

另有 15 个目录联接，全部指向现用 `neon-workbench/node_modules`，统计未跟随。清单不包含这些联接或它们的父目录。文件扫描、分配空间读取均无错误。

清单按卷号/文件身份去重：保留链接仍存在时计释放 0，全部链接都在本批时只计算一次。整批预算归账到清单最前一项，因此某类预算包含必须跨类一起删除才能释放的部分；每项另列“单独删除”的保守收益。证据见 `hardlink-impact.json.gz` 和 `inventory.json.gz` 的 hardlinks 字段。大体积路径元数据采用 gzip 保存；人类可读清单及 CSV/JSON 不压缩。删除一个链接不会修改其余链接内容；不得把这种目录删除改成覆盖或清空共享文件。最终卷可用空间仍须在执行前后实测，文件系统元数据、额外数据流、打开的文件句柄可能造成小幅差异。

## 清理策略与保留边界

- `.planning` 只删明确的旧运行时叶目录和过期轮次 ZIP，保留父目录中的源码、checkpoint、配置、验收报告及数据。旧测试安装将不能原地启动，重跑相应历史测试需要重建夹具。
- `.ai-runtime/versions` 不简单保留最近两版。保留当前版、已验证稳定版、旧 3.0.1 已确认版、含数据库的发布输入版，并递归保留它们的全部 `previous` 依赖，共 29 个版本。只提议退役另外 15 个候选：包括未采用候选和已经脱离保留链的旧分支。退役分支内部有历史 `previous` 引用，清单 JSON/CSV 逐项列出；这些分支整批退役后不能再激活，receipt 仍保留为证据。没有保留版本的 `previous` 指向本批目标。
- 保留链仍占较大空间，是遵守“有效引用不能破坏”的保守选择。若以后希望只留约 3–5 个运行时，须先明确批准停止保留完整历史逐级回退链，并调整回退记录/保留规则。本轮不擅自修改。
- 项目外 Staging 是 prepare 的来源记录。当前候选已有独立完整副本；activate/rollback 不读取 `source`。删除后只影响重做旧 prepare，需重新组装来源，不影响既有候选运行或切换。不得把这种来源引用描述成“从未引用”。
- 外部 `AI-OS-Preview-Staging/video-hover-icon-centered-20261023-stage-r1` 最终保留：它是当前版来源，且全目录没有多硬链接，可供后续评估作为固定开发目标；已有 build 路径允许此独立目录，无需先新复制一套。尚未启动它、绑定真实数据或改动原启动入口。另两份 stage 列入清理。
- Golden 的恢复演练副本可以删除：保留 Golden/payload 与演练树各 26,357 个文件，均与 recovery-manifest 逐项 SHA256 完全相同、没有额外文件。演练树中的素材、源码和 Git 副本均仍在 Golden 中。

- `.publish` 内 Runtime/Component ZIP 暂保留，不能只因名字或版本重复就推定内容完全由 Portable ZIP 覆盖。当前可确定的解压副本已足以释放空间。

## 最小开发方案评估

| 问题 | 结论与限制 |
|---|---|
| 源码能否直接运行？ | `npm run dev` 已可运行 Vite/React 热更新。当前仅代理 `/api` 到 3199；宿主桥接、登录会话、父页面初始化、`/output` 素材路径不是完整桌面等价环境，不能直接承诺全部真实业务热更新。 |
| 能否仅更新前端？ | 可以。已有 `deploy.mjs --dev-preview=build --preview-build-runtime=明确独立目录 --components=明确白名单` 走 component-deploy，按 SHA 比较，仅写入变更文件并备份，无需复制 Electron。必须先成功 build；本轮未执行。 |
| 能否复用一个开发运行时？ | 可以复用独立组装目录，已有 build 路径支持。它目前必须与原 Portable 目录不重叠，不能直接覆写当前受 receipt 完整性保护的候选。把开发版接入原启动器、同时保持完整性边界，还需要一个小而明确的开发目标/启动规则，不能只改复制命令。 |
| 是否每次退出？ | 前端 HTML/JS/CSS 由服务按请求读文件，更新后通常刷新即可；现有 development cache mode 可禁用静态缓存。Node 后端 require 模块需重启服务（按现有应用生命周期）；Electron main/preload、运行环境依赖、运行时指针切换需保存后正常退出并重新打开。页面刷新不替代后端重启。 |
| 是否需要新平台？ | 不需要。复用 Vite、现有 TypeScript/构建缓存、component-deploy、现有 runtime-paths 和 preview activate 即可。 |
| 源码如何回退？ | 先将实际有效源码和未跟踪文件纳入有意选择的 Git 检查点，之后逐项提交，按文件/提交 revert；不能 reset --hard 或用旧 HEAD 丢掉全部近期工作。稳定运行时作为第二层保障。 |

## 避免再次膨胀

目前没有发现现成的候选保留数量开关。建议先用简单工作约定和现有脚本：一个复用开发目录；保留当前、已确认稳定、必要的事务回退及原始/Golden；完整候选只在阶段验收创建。稳定版晋升需记录用户确认范围和 receipt/hash，不能按时间自动选择。

临时 stage/测试安装在验收结束、确认无有效输入引用后移除；正式包每版保留必要恢复资料，停止长期保留每轮重复解压目录。只保留唯一的源码/checkpoint/报告和必要变更备份，不能按目录年龄盲删。真实用户数据不复制为长期测试环境。

Git 已忽略主 Portable runtime/data、正常 dependencies/dist、部署备份；`.planning`、`.publish` 生成大目录缺少完整窄范围忽略规则，目前未被 Git 跟踪，但有误加风险。建议只为实际生成子目录/归档补 ignore，保留规划文档、独有源码与 provenance，不把整个 `.planning` 或 `.publish` 一概忽略。

现有组件机制值得复用；完整候选机制继续用于正式验收和发布。值得做的是小范围白名单、开发目标保护和操作约定，不值得重构部署系统。
